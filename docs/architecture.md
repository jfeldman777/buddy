# Buddy Alpha 0.01 — архитектура и утверждённый план

Документ фиксирует решения, принятые при согласовании [техзадания 001](spec-001.md). При расхождении с техзаданием действует этот документ.

## Принятые решения

- Архитектура: GitHub Pages (статическое PWA) + Cloudflare Worker + D1.
- Провайдер ИИ: OpenAI.
- Авторизация пользователя: passkey — основной способ, код восстановления — резервный.
- Авторизация разработчика: только passkey.
- Уведомления разработчику: Telegram-бот. Web3Forms/FormSubmit допустимы только для уведомлений, но не для хранения секретов и не для финансовой авторизации.
- Документы публикуются в Markdown; оригиналы `.docx` в репозиторий не выкладываются.

## Компоненты

### Клиент — `web/`, GitHub Pages

Адрес: `https://jfeldman777.github.io/buddy/`. Чистый JavaScript без сборки.

- Стартовая страница, PWA-манифест, service worker, значки, QR-код.
- Знакомство с Би, выбор голоса (Web Speech API), текстовый режим.
- IndexedDB: имя, голос, настройки, история диалога, журнал, оценки, разрешения и согласия.
- Просмотр, экспорт и удаление локальных данных.

### Сервер — `server/`, Cloudflare Worker + D1

Адрес: `https://buddy-api.<subdomain>.workers.dev`.

- Авторизация (WebAuthn, коды восстановления, сессии).
- Пробный доступ, заявки на финансирование, учёт бюджета и расходов.
- Обращение к OpenAI. Ключ хранится только в секретах Worker.
- Административные операции и журнал администратора.
- Уведомления разработчику.

Сервер по умолчанию не хранит полный архив реплик. Текст текущих реплик и (при согласии) переписка за сегодня с устройства проходят через Worker к OpenAI; в учёт попадают токены и стоимость. С **Buddy-011** при явном согласии А на сервере хранится **структурированная** личная память (факты/оценки/планы, учения, краткий контекст незавершённых тем и последняя реплика Би) — см. [buddy-011.md](buddy-011.md). Журнал деклараций и отображаемое имя остаются на устройстве. Бюджет общения А–Би (`buddy_chat_budget`) отделён от бюджета испытаний DCB ($10).

## Знакомство и пробный доступ

Знакомство с Би доступно без регистрации и оплаты.

- Выбор голоса, имя и стартовый диалог Би работают локально по сценарию, без ИИ и без сервера.
- Пробный разговор с настоящим ИИ — анонимный и ограниченный:
  - сервер выдаёт пробный токен после проверки Cloudflare Turnstile (защита от ботов, бесплатно);
  - у пробного токена собственный маленький бюджет в той же таблице `budgets` и те же правила резервирования;
  - ограничения: один пробный токен на устройство, лимит выдачи на IP в сутки, общий суточный потолок расходов на все пробные доступы;
  - при исчерпании пробного бюджета или общего потолка Би продолжает разговор по сценарию и предлагает оформить финансирование.
- Пробный бюджет переносится в учётную запись, если пользователь регистрируется с этого устройства.

## Авторизация

### Общие правила

- Сессия передаётся в заголовке `Authorization: Bearer <token>`; cookie не используются (Safari блокирует сторонние cookie).
- Токен сессии — 32 случайных байта; в D1 хранится только SHA-256; на устройстве — в IndexedDB. Срок — 30 дней со скользящим продлением; отзыв — удалением строки.
- `user_id` — случайный UUID, создаётся сервером. Сервер берёт `user_id` только из сессии, никогда из тела запроса.
- Учётная запись создаётся при переходе к финансированию. Имя на сервер не передаётся без отдельного согласия.

### Пользователь: passkey (основной способ)

1. `POST /auth/register/options` — одноразовый challenge (хранится в D1, живёт 5 минут), `rpId = jfeldman777.github.io`, `residentKey: required`.
2. `navigator.credentials.create()` → `POST /auth/register/verify` — проверка через `@simplewebauthn/server`, сохранение публичного ключа и счётчика.
3. Выдаётся код восстановления (показывается один раз) и сессия.

Вход: `POST /auth/login/options` → `navigator.credentials.get()` (без ввода логина) → `POST /auth/login/verify`. Passkey, синхронизированный через iCloud или Google, переживает очистку браузера и смену телефона.

Если устройство не поддерживает passkey, учётная запись создаётся только с кодом восстановления — с явным предупреждением.

### Пользователь: код восстановления (резервный способ)

- 20 символов base32 (100 бит) — перебор невозможен даже без ограничений; ограничения добавляются для защиты от нагрузки и утечек.
- В D1 хранится HMAC-SHA-256 кода с серверным секретом `RECOVERY_PEPPER`; сравнение — за постоянное время.
- `POST /auth/recover`: не больше 5 попыток в час с одного IP, общий счётчик неудач по сервису с автоматической паузой эндпоинта при всплеске, обязательная проверка Turnstile.
- После успешного входа старый код аннулируется; пользователю предлагается создать новый passkey и получить новый код.

### Восстановление оплаченного доступа

Бюджет, заявки и расходы хранятся на сервере и привязаны к `user_id`. После входа по passkey или коду восстановления оплаченный доступ возвращается полностью.

Если утрачены и passkey, и код: пользователь создаёт новую учётную запись и называет номер прежней заявки; разработчик переносит бюджет в административном интерфейсе. Перенос — отдельная операция с записью в `admin_audit`; старая учётная запись блокируется.

Локальный журнал после потери данных не восстанавливается — пользователь видит это предупреждение и кнопку «Экспорт».

Ограничение: passkey привязан к домену `jfeldman777.github.io` (общему для всех проектов на нём). При переезде на собственный домен вход по старым passkey перестанет работать; переход выполняется через коды восстановления.

### Разработчик: только passkey

- Регистрация как обычный пользователь; роль назначается командой с компьютера разработчика:
  `wrangler d1 execute buddy-db --remote --command "UPDATE users SET role='admin' WHERE id='…'"`.
  Веб-эндпоинта назначения администратора нет.
- Вход только с `userVerification: required`. Код восстановления администратору не выдаётся и не принимается: эндпоинт `/auth/recover` отказывает учётным записям с ролью `admin`. При потере passkey роль назначается заново той же командой.
- Сессия администратора — 12 часов.
- Каждый `/admin/*` проверяет роль по базе. Каждая операция пишется в `admin_audit`: кто, что, когда, старое и новое значение.
- `admin.html` публичен на Pages, но без авторизованного запроса не получает никаких данных.

## Защита API

CORS не считается защитой: он ограничивает только браузеры, а прямой запрос (curl, скрипт) его игнорирует. Защита строится на сервере.

- **Авторизация на каждом эндпоинте**, кроме `/health`, `/auth/*` и `/trial/start`. Эти три защищены отдельно.
- **Turnstile** на анонимных эндпоинтах, которые создают сущности или тратят деньги: `/trial/start`, `/auth/register/*`, `/auth/recover`.
- **Ограничение частоты** через Cloudflare Rate Limiting binding (бесплатно в Workers):
  - по IP — на анонимные эндпоинты;
  - по `user_id` — на запросы к ИИ (например, не больше 10 в минуту);
  - по сессии администратора — на `/admin/*`.
- **Ограничения размера**: тело запроса до 32 КБ; длина истории, которую клиент присылает для контекста ИИ, ограничена; `max_tokens` ответа фиксирован на сервере.
- **Общий предохранитель**: суточный потолок расходов на OpenAI по всему сервису; при достижении — блокировка платных запросов и уведомление разработчику. Независимо от этого в OpenAI для проекта Buddy установлен месячный бюджет.
- **CORS** — `https://jfeldman777.github.io` и `http://localhost:*` для разработки — как дополнительная мера против использования API чужими сайтами из браузера.

## Сервер этапа 4: как устроен и как развернуть

Сделано: учётные записи, passkey, коды восстановления, сессии, роль администратора, защита API. Бюджетов, оплаты и OpenAI на сервере пока нет (этапы 5–6).

- Код — `server/src/`, схема — `server/migrations/`, настройки Worker — `server/wrangler.toml`. В D1 нет полей для имён, разговоров и журнала; код восстановления хранится только как HMAC, токен сессии — только как SHA-256. Это проверяют автотесты.
- Клиент: `web/account.html` — вход (passkey или код), добавить passkey, новый код, выйти; открывается из «Настроек» чата пунктом «Войти». Создание учётной записи показывается только по адресу `account.html?create`: на сайте ссылки на него нет, на этапе 5 его откроет Би при оформлении доступа. `web/admin.html` — панель администратора. На сервер ходит только `web/api.js`, и только с данными для входа; модули с разговором и журналом его не подключают — это проверяют автотесты.
- Вход администратора: параметры passkey общие (`userVerification: preferred`), но сеанс администратора (12 часов, без продления) выдаётся только при роли `admin` в базе и подтверждённой личности (отпечаток, лицо, PIN). Без подтверждения администратор получает обычный сеанс без доступа к `/admin/*`.
- Ограничения частоты: Cloudflare Rate Limiting (`LIMIT_ANON` по IP и группе эндпоинтов — 20 в минуту, `LIMIT_USER` по учётной записи — 60 в минуту) плюс счётчики в D1 для `/auth/recover`: 5 попыток в час с IP; 100 неудач за 10 минут по всему сервису ставят вход по коду на паузу на 30 минут.
- Cron раз в 30 минут удаляет истёкшие challenge, сессии и старые счётчики.
- CORS в продакшене — только `https://jfeldman777.github.io`; `http://localhost:8080` разрешается только в локальном `server/.dev.vars`.

Локальный запуск: скопировать `server/.dev.vars.example` в `server/.dev.vars` и заполнить (для Turnstile — публичный тестовый секрет Cloudflare `1x0000000000000000000000000000000AA`), затем `npm run api:migrate:local`, `npm run api:dev` и `npm run serve`. Страница `http://localhost:8080/buddy/account.html` сама подключится к `http://localhost:8787`.

Развёртывание (один раз, с компьютера разработчика, из корня репозитория):

1. `npx wrangler login`.
2. `npx wrangler d1 create buddy-db` — вписать выданный `database_id` в `server/wrangler.toml`.
3. `npx wrangler d1 migrations apply buddy-db --remote --config server/wrangler.toml`.
4. В панели Cloudflare создать виджет Turnstile для домена `jfeldman777.github.io`.
5. `npx wrangler secret put TURNSTILE_SECRET --config server/wrangler.toml` — секретный ключ виджета; `npx wrangler secret put RECOVERY_PEPPER --config server/wrangler.toml` — случайная строка (например, `openssl rand -hex 32`). Pepper нельзя менять после запуска: старые коды восстановления перестанут подходить.
6. `npx wrangler deploy --config server/wrangler.toml` — запомнить адрес `https://buddy-api.<subdomain>.workers.dev`.
7. В `web/config.js` вписать этот адрес и публичный ключ виджета Turnstile, `npm run bump`, опубликовать сайт.
8. Администратор: зарегистрироваться с passkey на `https://jfeldman777.github.io/buddy/account.html?create`, взять номер учётной записи из `wrangler d1 execute buddy-db --remote --config server/wrangler.toml --command "SELECT id, created_at FROM users ORDER BY created_at DESC LIMIT 5"`, затем `--command "UPDATE users SET role='admin' WHERE id='…'; DELETE FROM recovery_codes WHERE user_id='…'"`. Выйти и войти снова по passkey.

## Бюджет и расходы

### Таблицы

Суммы хранятся в целых микродолларах (1 $ = 1 000 000).

- `payments_received` — деньги, фактически полученные разработчиком: `id`, `request_id`, `amount_micros`, `received_at`, `note`, `confirmed_by`. Не влияет на лимит напрямую.
- `budget_grants` — назначенные лимиты: `id`, `user_id`, `request_id UNIQUE`, `amount_micros`, `kind` (`self_paid`, `sponsored`, `trial`, `transfer`), `granted_by`, `created_at`.
- `budgets` — текущее состояние, одна строка на пользователя:
  `user_id PK`, `granted_micros`, `spent_micros`, `reserved_micros`, `status` (`active`, `blocked_cost_unknown`, `suspended`), `updated_at`,
  `CHECK (spent_micros + reserved_micros <= granted_micros)`, `CHECK (reserved_micros >= 0)`.
- `usage_reservations` — резервы: `id`, `user_id`, `idempotency_key UNIQUE`, `amount_micros`, `status` (`active`, `settled`, `expired`), `created_at`, `expires_at`.
- `usage_charges` — фактические расходы: `id`, `reservation_id UNIQUE`, `user_id`, `model`, `input_tokens`, `output_tokens`, `cost_micros`, `cost_basis` (`exact`, `estimated_max`), `price_table_version`, `created_at`.

Ограничение `CHECK` делает превышение лимита невозможным на уровне базы, даже при ошибке в коде.

### Начисление лимита

Одна транзакция D1 (`batch`): вставка в `budget_grants` и `UPDATE budgets SET granted_micros = granted_micros + :amount`. Повторное подтверждение той же заявки нарушает `UNIQUE(request_id)`, транзакция откатывается целиком — бюджет не начисляется второй раз. Статус заявки меняется только командой `… WHERE status = 'pending'`.

### Запрос к ИИ

1. Сервер считает строгую верхнюю границу стоимости: входные токены (по фактическому тексту) × цена входа + `max_tokens` × цена выхода, по таблице цен текущей версии. Модели нет в таблице цен — запрос отклоняется.
2. **Резерв** — одна транзакция:
   - `INSERT INTO usage_reservations (…, status='active', expires_at = now + 5 мин)`;
   - `UPDATE budgets SET reserved_micros = reserved_micros + :max WHERE user_id = ? AND status = 'active' AND granted_micros - spent_micros - reserved_micros >= :max`.
   Если `UPDATE` не изменил строку, транзакция откатывается и запрос отклоняется. SQLite выполняет транзакции последовательно, поэтому параллельные запросы не могут вместе превысить лимит; `CHECK` — вторая линия защиты.
3. Запрос к OpenAI.
4. **Списание** — одна транзакция:
   - `UPDATE budgets SET reserved_micros = reserved_micros - :max, spent_micros = spent_micros + :actual WHERE user_id = ? AND EXISTS (SELECT 1 FROM usage_reservations WHERE id = ? AND status = 'active')`;
   - `UPDATE usage_reservations SET status = 'settled' WHERE id = ? AND status = 'active'`;
   - `INSERT INTO usage_charges (…)`.
   Повторное списание того же резерва ничего не меняет: резерв уже не `active`, а `reservation_id` в `usage_charges` уникален.
5. **Стоимость не определена** (OpenAI не вернул число токенов) или фактическая стоимость больше резерва: списывается весь резерв (`cost_basis = 'estimated_max'`), `budgets.status = 'blocked_cost_unknown'`, разработчику уходит уведомление. Новые платные запросы блокируются до разбора.
6. **Повтор с тем же `idempotency_key`** не создаёт второй резерв.

### Зависшие резервы

Резерв, не списанный до `expires_at` (Worker прервался, сеть оборвалась), мог уже стоить денег в OpenAI. Поэтому он не освобождается, а списывается полностью с `cost_basis = 'estimated_max'` и пометкой для разработчика.

- Обработка: Cron Trigger Worker каждые 5 минут и дополнительно — перед каждым новым резервом этого пользователя.
- Та же транзакция, что и при списании, поэтому одновременная обработка cron'ом и запросом безопасна: сработает только одна.
- Разработчик может сверить такие списания с панелью использования OpenAI и вернуть разницу отдельной записью `budget_grants` с `kind = 'transfer'`.

## Голосовой ввод

- Распознавание речи браузера (`SpeechRecognition`), без сервера. Звук обрабатывает Google (Chrome, Samsung Internet) или Apple (Safari), но не разработчик; Би говорит об этом, когда просит разрешения.
- Микрофон включается только нажатием 🎤, на одну фразу. Постоянного прослушивания нет.
- Разрешение в два шага: согласие в Buddy (хранится на устройстве, отзывается в «Настройках»), затем системный запрос браузера.
- Распознанный текст вставляется в поле; отправляет его только человек.
- К распознаванию обращается только `web/listen.js`, и только после проверки сохранённого разрешения — это проверяют автотесты.
- В журнал программа записывает получение и отзыв разрешения, проверку разрешения перед включением и каждое использование микрофона (D1).

## Журнал поступков Би

Полный журнал хранится только в IndexedDB на устройстве пользователя. На сервер (`shared_journal_entries`) попадает только запись, которую пользователь явно отправил кнопкой «Отправить разработчику»; отправка сама регистрируется в журнале как факт.

Каждая запись журнала — один поступок Би с общим `event_id` и четырьмя раздельно хранимыми частями:

1. **`explanation` — объяснение Би** (из ответа модели): ситуация, цель, решение, заявленный мотив, декларации, на которые Би ссылается. Не требует раскрытия скрытых рассуждений модели.
2. **`actions` — фактические действия** (записывает программа, а не модель): выданные и отозванные разрешения, обращения к ИИ с номером резерва и стоимостью, отправка данных, показанные пользователю предложения, результат действия. Ответ модели никогда не записывается в эту часть.
3. **`compliance` — проверка соответствия декларациям D1–D7**: для каждой декларации — `соблюдено`, `нарушено`, `не применимо` или `не проверено`, кто проверял и основание.
   - Программная проверка по фактам из `actions` там, где это возможно: D1 (использование микрофона/камеры только при выданном разрешении), D2 (отправка данных только при согласии).
   - Самооценка модели отмечается как самооценка и не считается программной проверкой.
   - Расхождение между `explanation` и `actions` (например, Би заявил «не отправлял данных», а программа зарегистрировала отправку) записывается как нарушение.
4. **`rating` — оценка пользователя**: «Да», «Нет», «Не знаю», комментарий, время. Связана с `event_id`. Отрицательная оценка не означает автоматически нарушение деклараций.

## DCB-010

Тренировочный модуль Ди–Си–Би: `docs/dcb-010.md`, страница `web/dcb.html`, таблицы `dcb_*`, API `/dcb/*`.
Протоколы испытаний хранятся на сервере отдельно от личных диалогов Buddy. Общий бюджет первых испытаний — $10 с жёстким резервированием. Скрытое описание Си недоступно Би (раздельные промпты + автотесты).

## Этапы

1. **Каркас и стартовая страница.** Структура репозитория, документы в Markdown, декларации, стартовая страница, PWA, значки, QR-код, автотесты, публикация на Pages.
2. **Знакомство без ИИ.** Выбор голоса, имя, IndexedDB, текстовый режим, узнавание при повторном запуске.
3. **Журнал на устройстве.** Структура записи из четырёх частей, оценки, просмотр деклараций, экспорт и удаление.
4. **Сервер.** Worker, D1, миграции, passkey, коды восстановления, роль администратора, защита API.
5. **Финансирование.** Заявки А и Б, административная страница, уведомления.
6. **ИИ.** Пробный доступ, резервирование и списание, отображение лимита, расхода и остатка.
7. **Поведение Би.** Системная инструкция с декларациями, инициатива, объяснения, проверка соответствия.
8. **Альфа-испытание.** Проверка по критерию готовности на реальных смартфонах.
